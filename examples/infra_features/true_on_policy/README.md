# True On-Policy between Training and Inference

True on-policy ensures that the log probs generated by inference engine (SGLang) is strictly equal to the one generated by the training Engine.

## Examples

### Example 1

In this script, we provide a minimal example to use true-on-policy.

```bash
python examples/infra_features/true_on_policy/run_simple.py
```

### Example 2

This script contains more features for various use cases, and one flag is about the true on policy feature.

```bash
python scripts/run_qwen3_4b.py full-train --train-backend fsdp --true-on-policy
```

In order to quickly see the curve, you may use `--mode debug_minimal`, which will skip evaluation and run generation with a very short output sequence length. Since true on policy is unrelated to OSL or answer correctness, this can be used for quick experiments.

### Example 3: Qwen3-30B-A3B (MoE)

```bash
python examples/infra_features/true_on_policy/run_qwen3_30b_a3b.py --mode debug_minimal --r3
```

The `qwen3_moe_true_on_policy_v1` contract makes the FSDP trainer bitwise equal to SGLang's decode, which samples the tokens. The trainer uses the logprobs and routing recorded during sampling; nothing is re-scored. The contract covers Qwen3-30B-A3B (Base and Instruct-2507 too) with single-GPU rollout engines.

* Attention: SGLang's vendored FlashAttention-4 on both sides, in batch-invariant mode with one KV split. Its decode and prefill walk the KV in the same tiles. The trainer (`miles/backends/fsdp_utils/sglang_attn_bridge/hf_fa4_patch.py`) calls it the way SGLang's decode does, on a page-size-1 view of its packed documents. Gradients come from the deterministic `flash_attn.cute` backward.
* Experts: SGLang's Triton fused-MoE kernels at their deterministic config on both sides, with Triton backward kernels in the trainer. Routing is transformers' `Qwen3MoeTopKRouter`, which computes what SGLang's on-policy routing branch computes.
* SGLang plugin (`miles_plugins/sglang/true_on_policy.py`, a `sglang.srt.plugins` entry point): it registers `qwen3_moe_true_on_policy_v1` with SGLang, which only ships the dense contract, giving it the same model-agnostic runtime policy. It also sets the `top_k` that SGLang's on-policy routing branch needs and adds the routed-experts capture that the branch skips, so rollout routing replay (`--r3`) works. Reinstall Miles (`pip install -e .`) after pulling so that SGLang finds the entry point; without it the engines reject the contract name at startup.
* Old-policy logprobs: the contract passes `--use-rollout-logprobs`, so the PPO ratio uses the sampler's logprobs. `train/train_rollout_logprob_abs_diff` still compares the training forward with them on every step.

On one 8×B200 node (colocated, Qwen3-30B-A3B-Base, math prompts, R3, 12 steps × 256 samples with up to 8192-token responses), `train/train_rollout_logprob_abs_diff` is 0 on every step and the per-token dumps (`--dump-details`) show 0 mismatches in about 3.0M tokens. Rollout throughput is about 2040 tok/s for the node.

Megatron and TP rollout are not supported.

#### Quantized experts

True-on-policy runs can quantize the routed MoE experts to block FP8, MXFP8, MXFP4 or NVFP4. Only the routed experts are quantized: attention, router, norms, embeddings and LM head stay in bf16, and the trainer keeps fp32 master weights. In every format the trainer's expert forward runs the sampler's kernels on the same quantized weights and activations, so the two stay bitwise equal. The backward is a bf16 GEMM (fp32 accumulation) on the dequantized operands, dequant(Q(W)) and dequant(Q(X)), and the gradients go to the master weights.

The formats fall into two cases, depending on whether SGLang already has a batch-invariant kernel for them:

* Block FP8 does. The engines serve an FP8 checkpoint through SGLang's own FP8 path, and the trainer calls the same batch-invariant kernel.
* MXFP8, MXFP4 and NVFP4 do not: SGLang's kernels for them autotune their tiling by batch size, so they are not batch-invariant. Miles brings its own batch-invariant kernels and runs them on both sides; the engines keep a bf16 model and the SGLang plugin swaps the kernels in.

On one 8×B200 node (R3, `--mode debug_minimal`, 4 steps each), `train/train_rollout_logprob_abs_diff` is 0 on every step in all four formats.

##### Block FP8: SGLang's FP8 path

W8A8 with e4m3 weights in 128×128 blocks and fp32 scales; activations are quantized per 128-wide token group.

```bash
# once: an experts-only FP8 copy of the model; Miles syncs the trainer's weights before the first rollout
python tools/convert_hf_to_fp8.py --model-dir /root/models/Qwen3-30B-A3B-Base \
    --save-dir /root/models/Qwen3-30B-A3B-Base-FP8-experts --strategy block --block-size 128 128 \
    --extra-high-precision-layers-hf self_attn

python examples/infra_features/true_on_policy/run_qwen3_30b_a3b.py --mode debug_minimal --r3 \
    --rollout-fp8-checkpoint /root/models/Qwen3-30B-A3B-Base-FP8-experts
```

The engines serve the FP8 copy. The trainer reads its `quantization_config` (`miles/backends/fsdp_utils/quantization.py`): each weight sync quantizes the experts with the kernel the trainer uses, and the trainer's forward runs SGLang's FP8 W8A8 Triton fused-MoE path. Weight sync rejects a checkpoint that quantizes anything other than the routed experts.

##### MXFP8, MXFP4 and NVFP4: Miles' kernels on both sides

```bash
python examples/infra_features/true_on_policy/run_qwen3_30b_a3b.py --mode debug_minimal --r3 --moe-quant mxfp8  # or mxfp4, nvfp4
```

| `--moe-quant` | elements | block scale | MMA instruction |
| --- | --- | --- | --- |
| `mxfp8` | e4m3 | e8m0 per 32 | `tcgen05.mma kind::mxf8f6f4 block32` |
| `mxfp4` | e2m1 | e8m0 per 32 | `tcgen05.mma kind::mxf4 block32` |
| `nvfp4` | e2m1 | e4m3 per 16, times an fp32 scale per expert (weights) or per token (activations) | `tcgen05.mma kind::mxf4nvf4 block16` |

The kernels are in `miles/kernels/moe/mx_fused_moe.py` (Triton `tl.dot_scaled`). The quantizers work row by row and the GEMM uses one fixed tile config without split-K, so the kernels are batch-invariant. NVFP4 uses a per-token activation scale for the same reason.

The trainer quantizes its bf16 experts on every forward. The engines receive bf16 weights; after each weight sync the SGLang plugin re-quantizes the experts in place into a cached buffer, so captured CUDA graphs stay valid. The launcher sets `MILES_MOE_QUANT` for every process to select the format.

### What is Expected to Observe

After running the training, you can see in wandb that the metric `train/train_rollout_logprob_abs_diff` should be exactly `0`. This indicates that there is no difference between the log probabilities from the training and the inference. Without the feature enabled, this value should be nonzero.

## How it is Implemented

The core idea is to make each and every operation in training and inference be bitwise equal. The main code is implemented in [#566](https://github.com/THUDM/slime/pull/566) and [SGLang#12058](https://github.com/sgl-project/sglang/pull/12058).

Briefly speaking, we handled the following components to make them aligned:

* Attention: We use the [Flash Attention 3](https://github.com/Dao-AILab/flash-attention) backend for both training and inference, since it achieves bitwise equal between prefill and decode operations.
* GEMM: We use [DeepGEMM](https://github.com/deepseek-ai/DeepGEMM) for fast matrix multiplication while preserving true-on-policy, thanks to its algorithm to pick things like tensor core instructions ([SGLang#12142](https://github.com/sgl-project/sglang/pull/12142)).
* Batch invariant kernels: This is a prerequisite for true on-policy, and we use [the ones](https://github.com/thinking-machines-lab/batch_invariant_ops) from the Thinking Machines Lab.
* Torch compile: We also utilize [`torch.compile`](https://docs.pytorch.org/docs/stable/generated/torch.compile.html) to speed up by avoiding many tiny kernels.
* We align numeric operation details between the two systems for simplicity, such as op dtype, detailed kernels, etc. Some operations can also be compiled to speedup ([#603](https://github.com/THUDM/slime/pull/603), [SGLang#12161](https://github.com/sgl-project/sglang/pull/12161)).

In order to more easily align the two parts, we use SGLang's [dumper](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/debug_utils/dumper.py) tool for quick comparisons. (Need [#12622](https://github.com/sgl-project/sglang/pull/12622) and [#12623](https://github.com/sgl-project/sglang/pull/12623) for most convenience.)
